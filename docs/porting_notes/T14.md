# T14 (#14) Costs and Claim (agent: muse)

- Costs' static tables load at module import, in Java's static-initializer
  order (method, cost CSVs, config defaults, adjustment CSVs). Config is
  read at import time, exactly as Java reads it at class-load time.
- Bug found and fixed while writing the parity tests: costs.py referenced
  `Person.STATE` at runtime but imported Person only under TYPE_CHECKING,
  so every determineCostOfEntry call raised NameError. Person is now a
  runtime import (no cycle: costs is otherwise imported lazily).
- CostData keeps Java's protected-class shape as a module-level class, also
  bound as Costs.CostData; ClaimCost/ClaimEntry likewise bound onto Claim.
  ClaimEntry is a Java inner class: the Python ClaimEntry stores its
  enclosing Claim in `.claim`, set by Claim's factory; assign_costs asserts
  it, matching Java's implicit outer reference.
- Java's NumberFormatException path in parseCsvToMap prints the error and a
  stack trace to System.err; the Python port prints the two message lines
  to stderr (a Java stack trace has no Python counterpart) and skips the row.
- Entry.getCost() truncates to 2dp DOWN in HealthRecord.determineCost
  (T08); Costs.determineCostOfEntry itself returns the unrounded double.
- ClaimEntry.assignCosts never assigns the `adjustment` field: the value
  returned by plan.adjustClaim is subtracted from the running balance only.
  The port keeps this exactly (covered by a unit test).
- Probe design: entry times are birthdate + 30 days, inside the first
  no-insurance plan record's year (a PlanRecord stops at the next
  enrollment period, birthdate + 1 year), because building a Medication
  builds its Claim and the Claim constructor requires a plan record then.
- Immunizations have no cost table rows upstream (immunizations.csv is
  header-only), so every immunization lookup exercises the default-cost
  path; the probe still runs them per state/seed.
- Claim parity is integration-gated on T15/T16 (see PR body): even a
  no-insurance claim needs CoverageRecord/PlanRecord (T16) and
  InsurancePlan (T15), all still skeletons in Python.
- Parity bug found in a dependency (T07, not fixed here per AGENTS.md §4;
  see PR "Problems found"): CostsProbe lookups match Java exactly on
  ~13,000 of ~13,002 lines. The 2 misses (Texas seed 12345, procedures
  D0501 and D7453) are 1-ulp differences traced to
  `Distribution._java_log` in src/synthea/engine/distribution.py (T07),
  which delegates to Python's correctly rounded `math.log`. JDK 21
  `Math.log` returns a value 1 ulp lower for the two draws involved
  (1-rand = 0.2152045477721394 and 0.9366031367366193); substituting
  log-1ulp into the exponential chain reproduces Java's costs
  bit-for-bit in both cases. T01 already carries an fdlibm
  `StrictMath.log` port (javacompat random) for the same reason;
  Distribution's EXPONENTIAL path needs the same treatment in a T07
  fix task. DistributionProbe's own cases apparently never drew a
  value where the two logs disagree.
