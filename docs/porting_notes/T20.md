# T20 — Clinical States + ReactionProbabilities

Scope: the clinical half of `src/synthea/engine/state.py` (every State
subclass not owned by T19) and `src/synthea/engine/reaction_probabilities.py`.

## ReactionProbabilities (done)

- Ported with its JUnit test (`tests/unit/test_reaction_probabilities.py`,
  6 tests, all passing).
- Java's distribution sampling works on `float` (32-bit) probabilities;
  the port reproduces that with an explicit float32 rounding helper so
  cumulative-probability edge behaviour matches the JVM exactly rather
  than Python's float64.

## Clinical states (implementation complete)

- All clinical State subclasses are ported: Encounter/EncounterEnd
  (incl. diagnosePastConditions and renewChronicMedicationsAtWellness),
  AttributeAssignableState, OnsetState, ConditionOnset, ConditionEnd,
  AllergyOnset, AllergyEnd, MedicationOrder (+applyFeatures),
  MedicationEnd, CarePlanStart, CarePlanEnd, Procedure, VitalSign,
  Observation/ObservationGroup/MultiObservation, DiagnosticReport
  (+panelAlreadyRecordedAtThisTime), ImagingStudy, Symptom, Device,
  DeviceEnd, SupplyList (+SupplyComponent), Vaccine.
  `check_port_map.py --task T20 --no-stubs` reports 0 errors.
  MedicationOrder.writeObject/readObject follow the T13 convention:
  Java serialization is out of scope.
- AllergyEnd's codes branch calls `conditionEnd` in Java (not
  allergyEnd); ported literally.
- Encounter.process calls `EncounterModule.createEncounter` (T22);
  the Python stub declares the `code` parameter as non-null `Code`
  while Java passes null — the call site casts, and T22 should widen
  that parameter to `Code | None` when it ports the method.
- Observation#process in Java reads the `threadExpProcessor` field
  directly and never calls `getExpProcessor()`, so an expression-only
  Observation yields a null value unless the field was populated
  elsewhere; ported literally.
- Remaining for the task: the StateProbe full-module runs
  (acceptance criterion 1) and the rest of StateTest +
  GlobulinObservationTest. Full-module runs transitively exercise
  the T21–T24 core modules, which are still shells, so probe
  scenarios will be dependency-gated the way earlier tasks gated
  theirs.

## StateTest ports (tests/unit/test_state_clinical.py)

- Ported and passing: condition_onset, condition_onset_last_onset_time,
  allergy_onset, gmfTwoVitalSign, vitalsign, symptoms_last_updated_time,
  gmfTwoSymptom, symptoms, symptoms50.
- Skipped in-file (T22): gmfTwoProcedure, gmfTwoObservation — the
  record methods create an encounter via
  EncounterModule.createEncounter, which is a T22 stub. The remaining
  encounter-driven StateTest tests are likewise T22-gated.
- Bug found in shared machinery: `_fill_state_from_json` had no
  conversion for the state fields `vital_sign` (JSON display string
  stayed a plain string, so Person.setVitalSign keyed the dict by
  string and getVitalSign raised KeyError), `activities`,
  `reactions`, `supplies`, or `series` — Gson builds real objects
  for all of them. Cases added; the VitalSign StateTest tests caught
  it. This filler is shared with T19's states.
