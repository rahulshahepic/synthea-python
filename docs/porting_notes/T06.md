# T06 (#6) helpers: Utilities, TimeSeriesData, Telemedicine (agent: muse)

- Claimed from main aa0f6c8. Dependencies T01 (#1) and T03 (#2) closed.
- Scope: `src/synthea/helpers/utilities.py`, `time_series_data.py`,
  `telemedicine.py`; probe `UtilitiesProbe`; parity + unit tests for the area.
- Stubs kept (listed in the PR): `getGson` (Gson bound to engine Logic/State
  type adapters), `parseYamlToResources` (FHIR), and the
  `walkAllModules(BiConsumer)` overload (module roots come from engine
  `Module`). The `walkAllModules(Path, Consumer)` overload is ported.
  Each kept stub's message contains "out of scope".
- Utilities uses two different calendars and the port keeps them distinct:
  `convertCalendarYearsToTime`/`getYear`/`getMonth`/`getAnniversary` use
  `java.util.GregorianCalendar`, a hybrid Julian/Gregorian calendar with
  cutover at Gregorian 1582-10-15 (the epoch day after Julian 1582-10-04),
  while `localDateToTimestamp`/`timestampToLocalDate`/`parseDateRange` use
  proleptic Gregorian `java.time.LocalDate`. Verified against JDK 21:
  `convertCalendarYearsToTime` matches for every year -2000..3000 in the
  probe, including the Julian range.
- `Calendar.YEAR` has no year zero: `getYear` returns the YEAR field only
  (era dropped), so astronomical year 0 reads back as 1 (BC) and -5 as 6
  (BC) — JDK-verified. `convertCalendarYearsToTime(years)` sets YEAR with
  era AD, which the JDK resolves to astronomical year `years`.
  `getAnniversary` does its arithmetic on the YEAR field within the
  original era, so an anniversary on a BC date moves backwards
  astronomically; resolution is lenient (Feb 29 + 1y -> Mar 1).
- `convertTime` overloads differ and are dispatched on the Python type
  (int -> long overload, float -> double overload, mirroring Java's
  widening preference): the long "years" case multiplies by
  `(long) 365.25` == 365 with a *wrapping* long multiply before the
  saturating `TimeUnit.toMillis`, while the double "years" case uses
  365.25 and truncates after multiplying. All `TimeUnit` conversions
  saturate to Long.MAX/MIN instead of overflowing.
- `compare(Boolean, Boolean, op)`: every ordering operator and `!=`
  returns `lhs != rhs` in the Java source; reproduced exactly.
  `compare(Code, Code, op)`: equality is `HealthRecord.Code#equals`, which
  compares system and code only (not display); it is inlined in
  `utilities.py` because the Code port (T08) is still a stub.
- Python has one `compare()` where Java has six overloads. For a null lhs
  it follows the Object overload (false for every non-nil operator). The
  statically typed overloads (Double/Boolean/String/Integer) instead throw
  NullPointerException for a null lhs with a supported operator, because
  they unbox it. Probe rows for typed overloads therefore cover null lhs
  only on the nil operators and on an unsupported operator, where both
  behaviours agree (false / the nil result). All Synthea engine call sites
  use the Object overload.
- `primitive()`: the Python analogue of a Gson `JsonPrimitive` is the plain
  value it wraps (bool/int/float/str). A `Character` primitive is a string
  in Gson (`isString()` is true), so a one-character str is the analogue.
  Numbers go through `getAsDouble()` and integral results come back via
  the saturating `(int)` cast; NaN stays a Double (rint(NaN) != NaN).
- `parseDateRange` returns commons-lang3 `Range<Long>`, an external
  library type — not `Components.Range`. It is ported as the
  `LongRange(minimum, maximum)` NamedTuple in `utilities.py`.
  `Range.between` *sorts* its endpoints (verified against commons-lang3
  3.12.0), so a reversed range is not an error.
- `SYNTHEA_VERSION` / `getSyntheaVersion`: `version.txt` is generated by
  the Java build (`versionTxt` task writes the git HEAD hash) and is
  gitignored, so the Python checkout normally has no such resource and the
  version is the Java default "synthea-java". The probe records resource
  reads for other files exactly, and the parity test tolerates a golden
  that has version.txt content where Python has none (and vice versa).
  Java also prints a stack trace when the read fails; that print is
  omitted because this branch is taken on every Python import.
- `readResource`: Guava `Resources.getResource` failures raise
  IllegalArgumentException (mirrored as ValueError); a missing free path
  under `readResourceOrPath` surfaces Java's NoSuchFileException
  (mirrored by Python's FileNotFoundError/OSError). Decoding is UTF-8
  with replacement, like `new String(bytes, UTF_8)`/Guava.
- `enableReadingURIFromJar` is a no-op in the port: it is a JDK
  jar-filesystem workaround, Java itself does nothing for non-"jar" URIs,
  and the Python port never reads resources from a jar.
- `strToObject` takes the Java class as a name string (or the Python types
  bool/int/float for Boolean/Integer/Double), because Python's single int
  type cannot distinguish Byte/Short/Integer/Long. Float results are
  rounded to float32.
- `convertRiskToTimestep` uses a Math.pow mirror: Java overflow yields
  +-Infinity and a negative base with a fractional exponent yields NaN,
  where Python's math.pow raises. Verified bit-exact against JDK 21
  Math.pow on all 550 probe risk rows before the golden was generated.
- Telemedicine: before `TELEMEDICINE_START_DATE` no random draw is made;
  the port preserves that (the person's RNG stream is untouched), which
  the unit tests assert explicitly.
- TimeSeriesData: the `(List, double)` constructor stores the list by
  reference, as Java does; the `(int, double)` capacity is an ArrayList
  sizing hint whose only observable effect is IllegalArgumentException
  for a negative capacity (mirrored as ValueError).
- tests/unit/test_skeleton.py: T06 added to the implemented-tasks
  exclusion set, following the T04/T05 convention.
- Fixes from the first CI run (java-golden failed, test job skipped),
  all verified locally against JDK 21 goldens (full suite with
  PARITY_REQUIRED=1: 366 passed):
  - UtilitiesProbe did not compile: two lambdas captured non-final loop
    variables (`year`, `a`). Both now bind a final local inside the loop.
    This was the sole cause of the CI java-golden failure; with it fixed,
    every probe compiles and runs and the scenario is deterministic.
  - `convertTime` long overload: the "months" (30 * value) and "weeks"
    (7 * value) cases are wrapping long multiplies in Java, like "years";
    the port originally multiplied in Python big-int and saturated to the
    wrong sign on overflow. All three now wrap before the saturating
    TimeUnit conversion.
  - `compare` Object overload with a null rhs: Java builds its
    "Cannot compare" message with `rhs.getClass()`, so a null rhs throws
    NullPointerException (mirrored as TypeError), not the RuntimeException
    a plain type mismatch gets. The port now mirrors that.
  - Parity-test double comparisons (primitive, convertRiskToTimestep)
    now compare `Double.toString` output instead of `==`, which is exact
    for NaN and -0.0 (the probe serializes results with Double.toString).
  - LocalDate range deviation: the port maps `LocalDate` to
    `datetime.date` (minimum year 1), so the probe's epoch-day sweep
    starts at 0001-01-01 (-719162) instead of 0000-01-01; Java years < 1
    are outside the port's representable range. Every other sweep point
    (to 9999-12-31) is covered.
