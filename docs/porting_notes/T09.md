## Port decisions

- All Java `ConcurrentHashMap` fields use `JavaConcurrentHashMap` from T02 (with
  `key_type="long"` for the `Map<Long, …>` maps), per the issue: hash iteration
  order is observable in `Person#getSymptoms` (stable sort ties),
  `Person#addressLargestSymptom` (first maximum wins) and
  `ExpressedSymptom#getSourceWithHighValue`.
- `Person#vitalSigns` is keyed by the `VitalSign` enum. Java enum `hashCode` is
  identity-based, so the Java map's iteration order (visible only in
  `getVitalSign`'s not-set exception message) is not deterministic across JVM
  runs; the port's map iterates by the enum's string hash instead. Canonical
  dumps sort vital signs by name on both sides, and the probe records only the
  exception kind for an unset vital sign, never the message.
- `Person#age` returns a small `Period` class defined in `person.py` (the port
  has no `java.time` module yet), implementing `Period.between`'s exact
  java.time algorithm, including the month-end clamping branches for positive
  and negative periods. `BIRTHDATE_AS_LOCALDATE` caches a `datetime.date`.
- `Person#getLonLat` returns a `Point2DDouble` class defined in `person.py`
  (Java `java.awt.geom.Point2D.Double`); `getX`/`getY` delegate to it.
- `Person#randUUID` returns `uuid.UUID`, as Java does and as the T04 skeleton
  annotated: T01's `DefaultRandomNumberGenerator#randUUID` represents Java
  UUIDs as strings internally, so Person converts that string at its own API
  boundary. (First version returned `str`; that broke T08's merged
  `HealthRecord.Entry`, whose `uuid` field is typed `UUID` — mypy failure on
  the merged branch, fixed 2026-11-05.)
- `Person#rand` stays arity-0, exactly as declared in Person.java (the
  skeleton signature test enforces declared arities per class). The
  `RandomNumberGenerator` interface default overloads (range, array, choices)
  live on T01's `DefaultRandomNumberGenerator` in the port, reachable as
  `person.random.rand(...)` with identical draws; the probe exercises them
  through the Java interface defaults and the Python driver mirrors them
  through the person's DRNG.
- Java quirk reproduced: `Person#addCurrentProvider` only puts the new entry
  when the `currentProvider` map does not exist yet; when the map already
  exists the supplied context/provider is silently dropped.
- Java quirk reproduced: `Person#addressLargestSymptom` on a person with no
  symptoms dereferences `symptoms.get("")` and throws NullPointerException;
  the port raises `TypeError` (this codebase's NPE mirror) in that case.
- Java `Boolean`/`Long` unboxing NPEs (e.g. `SymptomSource#addInfo` with a null
  `addressed`, `ConditionWithSymptoms#addSymptoms` with a null onset time) are
  mirrored as `TypeError`.
- `Person#getProvider`'s fixed-record branch (`identity.Entity`) is out of
  scope per the issue: `ENTITY` stays `None` in attributes and the branch
  raises `NotImplementedError` with an "out of scope" message if it is set.
- `ExpressedSymptom.SymptomSource#symptom` (the `@JSONSkip` enclosing-instance
  field) is tracked as a plain attribute; `ExpressedSymptom#onSet` binds it.
  The other inner classes' implicit enclosing references are not read by any
  Java code and are not tracked.
- `SymptomSource#getSourceWithHighValue`'s two Java branches (first unresolved
  source, then strictly greater) assign identical values and are combined into
  one condition; behaviour is unchanged, including the value-0 first-source
  case.
- Probe fix (2026-11-05, found via the CI java-golden failure on e337432,
  annotation "Person does not have insurance at time 5000000"): every Java
  `Encounter` constructs a `Claim`, whose constructor calls
  `coverage.getPlanRecordAtTime(start)` and throws on a person with no plan
  history. `PersonProbe` now follows the upstream `HealthRecordTest` /
  `HealthRecordProbe` setup: `PayerManager.loadNoInsurance()` in `main`, and
  `coverage.setPlanToNoInsurance(birthdate)` in the records scenario. The
  no-insurance plan's `determinePlanOwnership` returns early, so enrolment
  draws no RNG; its only Person-visible effect is
  `insurance_status = "none"`, which `CoverageRecordDouble` mirrors.
  Same fix round: each Java `Encounter` draws TWO UUIDs from the person
  (the entry's own, then its Claim's), so `EncounterDouble` now draws a
  second UUID for the claim; without it the records cases' RNG counts and
  the second encounter's uuid would diverge from the golden.
- Two real port bugs found by comparing against the locally generated
  PersonProbe golden (CI `test` job failure on 6f0c924, reproduced locally):
  (1) `getProvider`/`setProvider` built the attribute key as
  `"preferredProvider" + <StrEnum value>` (uppercase, e.g.
  `preferredProviderWELLNESS`); Java concatenates the enum itself, whose
  `toString()` lowercases (`preferredProviderwellness`). Fixed in
  `person.py` to use `EncounterType#toString`, including the
  "Unable to find provider: …" message. (2) `EncounterDouble` typed
  encounters with `str(type)`; Java's `Encounter.type` is
  `EncounterType.toString()` (lowercase), as T08's real
  `encounter_start` already does via `type.to_string()`.
  Also: Java enrolment's age check populates the `birthdate_as_localdate`
  attribute cache, which `CoverageRecordDouble.set_plan_to_no_insurance`
  now mirrors by calling the real `age_in_decimal_years`.
