## Deviations and Java quirks reproduced
- `Provider()` constructor UUIDs: Java assigns `UUID.randomUUID()` to `uuid`/`locationUuid`, which is nondeterministic in Java too and is overwritten by `csvLineToProvider` before any observable use. The port uses `uuid.uuid4()` there only (a deliberate, scoped exception to PORTING_GUIDE §5: there is no seed in the Java code either).
- `providerByUuid` is a `JavaHashMap` because `getProviderList()` iterates its values (PORTING_GUIDE §3). `clinicianMap` is a plain dict (lookup/put only, never iterated by ported code), `statesLoaded` a plain set (contains/add only), and `servicesProvided` a plain set (contains/addAll only; canonical dumps sort service names on both sides).
- Utilization: Java's Guava `HashBasedTable<Integer, String, AtomicInteger>` is modelled as `dict[tuple[int, str], int]` (cell -> counter value); `get_utilization()` returns that dict. This corrects the T04 skeleton's `dict[int, str]` annotation. The skeleton's `coordinates: float` / `get_lon_lat() -> float` annotations were likewise corrected to `Point2DDouble`, and `bed_count` to `int | None` (Java `Integer`).
- `writeObject`/`readObject` (Java serialization hooks) remain stubs raising `NotImplementedError` with "out of scope" in the message: Java serialization has no Python counterpart and is not in the issue scope (allowed by `check_port_map --no-stubs`).
- `UUID.nameUUIDFromBytes` is replicated by a private helper in `provider.py` and `clinician.py` (MD5, version-3/variant bits forced, UTF-8 bytes, formatted via `javacompat.java_uuid`); javacompat has no such helper and editing it is out of T13 scope.
- `locationUuid` base reversal: Java `StringBuilder.reverse()` reverses UTF-16 code units; the port reverses Python code points. Identical for BMP text (all provider names in the shipped CSVs are BMP); astral-plane characters in a name would reverse differently.
- The `cmsPin` (>14) / `cmsUpin` (>12) length checks use Python `len` (code points) where Java `String.length()` counts UTF-16 code units; identical for BMP data.
- `generateClinicianList` builds the clinician identifier as `Long.parseLong(loaded + "" + i)` — string concatenation of the *current static* `loaded` count and the loop index — reproduced exactly, including that `loaded` grows as providers are inserted.
- `Clinician.populationSeed` is never set by the Java constructor (stays 0); reproduced. `Clinician.incrementEncounters`/`incrementProcedures` return the pre-increment count (`encounters++`); reproduced.
- `loadProviders(Location, random)`: Java catches `IOException` around the two load groups; Python's `read_resource` raises `ValueError`/`OSError` for a missing resource, so the port catches `(OSError, ValueError)` in the same two scopes, printing the same ERROR (main group) / WARNING (optional group) lines to stderr.
- `MAX_PROVIDER_SEARCH_DISTANCE`: the Java code default is 2, but `synthea.properties` sets `generate.providers.maximum_search_distance = 1000`; the port reads it through `Config.get_as_double(..., 2)` exactly as Java does, so 1000 wins on both sides.
- `ProviderFinderNearest`: the veteran check streams over the *original* providers list (`anyMatch` VETERAN), not the filtered options; reproduced. `Point2D.distance` in the finders replicates the JDK 21 implementation `sqrt((x2-x1)^2 + (y2-y1)^2)` in a private helper, because `person.py`'s `Point2DDouble` has no distance method.
- Provider static initializers (`USE_HOSPITAL_AS_DEFAULT`, `providerMap`, `MAX_PROVIDER_SEARCH_DISTANCE`, `providerFinder`) are initialized from Config in Java class-load order; `providerFinder` is assigned at module bottom, following the `Names.names` precedent, because building it imports the finder classes.

## Problems found
- Person (T09) has no `distance` method. Java's Person inherits `QuadTreeElement`'s default `distance`, which `QuadTree.query` calls on the query point; Python's Person defines `get_x`/`get_y`/`get_lon_lat` but no `distance`, so `Provider.find_service` / `find_service_new_provider` raise `AttributeError` for a real Person until T09 adds it. The parity test bridges this in tests only, assigning the interface-default distance to the ops-case query persons as an instance attribute. Provider and Clinician implement `distance` themselves, as their Java interfaces provide the default.
- A real Python `Person` cannot be constructed without T16: `Person.__init__` builds `CoverageRecord` (still a T16 stub raising `NotImplementedError`), and HealthRecord encounters need T14's Claim. Following T09's own component-test pattern, the parity and unit tests patch `person_module.HealthRecord` / `CoverageRecord` with the `tests/parity/person_doubles.py` doubles (construction plumbing only). Production Provider code calls the real Person unconditionally.
