# T18 (#18) Transition (agent: muse)

Bundle note: claimed as the primary of the §3a engine-state-machine bundle
(#18 T18, #19 T19, #20 T20). This file covers T18 only; T19/T20 have their
own notes files.

- LookupTableKey.equals is asymmetric and is reproduced exactly, including
  the boxed `==` quirk: `(this.age == that.age)` / `(this.time == that.time)`
  compare Integer/Long *references*, so two distinct boxed values are equal
  only inside the -128..127 cache range (see `_java_boxed_equals`). The
  time branch also differs by direction: a row key (time null, timeRange
  null) compared *against* a person key yields timesMatch=false, while the
  person key compared against the row key leaves timesMatch=true ("do
  nothing. Time will always be populated in one of them").
- Because HashMap lookup uses the *lookup* key's equals and a Python dict
  uses the stored key's, the lookup tables are stored in `LookupTableMap`,
  a small list-backed map in transition.py implementing Java's get/put
  direction. javacompat's JavaHashMap cannot be used: all keys hash to
  their attributes list, same-attribute rows share a bucket, and Java
  treeifies such buckets tie-breaking by System.identityHashCode, which is
  not reproducible (PORTING_GUIDE §7). The map is never iterated by
  Transition — only get/put — so the linear scan loses nothing observable.
- LookupTableTransition.attributes is an instance field that Java only
  sets on the instance that loads the table (static `lookupTables` cache).
  Later instances for the same table keep attributes == null and their
  follow() throws (NPE in Java, TypeError here). Reproduced; the probe
  follows only the first instance per table, like a fresh Synthea run.
- Age ranges use org.apache.commons.lang3.Range (Range.between sorts its
  endpoints), modelled as `IntRange(minimum, maximum)` in transition.py,
  mirroring the LongRange pattern Utilities.parseDateRange already uses
  for time ranges. This is not Components.Range.
- Range.toString is the commons-lang3 "[minimum,maximum]" form, used by
  LookupTableKey.toString; the Java list toString is "[a, b]".
- Probe scripting discovery (also relevant to T19): Utilities.getGson()'s
  Logic deserializers *mutate* the JsonObject they read (they remove
  "condition_type" from condition objects). Anything that inspects module
  JSON after Gson deserialization sees the stripped tree. The probe takes
  a pristine deep copy before constructing transitions; the Python mirror
  does the same.
- tests/logic_support.build_logic (T17) passes a numeric JSON `code`
  through as an int, where Gson would give Code.code the number's literal
  text (String field). tests/transition_support normalizes code values to
  str before calling build_logic, instead of editing T17's file. Worth
  fixing in logic_support if a T17 follow-up is opened: with an int code,
  ActiveCondition.check_code raises "Key outside Java Integer range" for
  SNOMED codes above 2^31.
- TransitionTest and LookupTableTransitionTest are ported at transition
  level (tests/unit/test_transition.py): the JUnit versions drive
  Module.process (T19) and ConditionOnset states (T20) from this same
  bundle. For these fixtures Module.process consumes no RNG draws beyond
  the transition's own, verified by the exact JUnit counts (15/55/30,
  100/0/0, 0/0/100, 76/8/16) reproducing with direct follows on a single
  Person(19L). The lookuptablitis scenarios assert the chosen target state,
  which the JUnit tests assert indirectly via the onset condition (the
  fixture CSV gives it probability 1). The Module-level versions should be
  added when T19/T20 land in this bundle.
