# T25 (#25) Exporter / ExportHelper / CSVFileManager / CSVConstants (agent: muse)
- CSVConstants.NEWLINE is Java `System.lineSeparator()`; the port keeps "\n" (the golden/CI
  environment is Linux, and Synthea's own CSV output is defined with the platform separator).
- ExportHelper date formatting goes through java.util.GregorianCalendar (via FastDateFormat),
  whose default cutover is hybrid: instants before 1582-10-15 are formatted with Julian
  calendar rules. Verified against the probe: epoch millis -62135596800000 (proleptic
  0001-01-01) formats as "0001-01-03". The port implements the Julian branch for pre-cutover
  instants. ExportHelper.nextFriday mixes Calendar field extraction with proleptic
  LocalDate arithmetic; the port uses day-count arithmetic, which is identical for all
  post-cutover timestamps (every realistic Synthea time) and does not reproduce the
  pre-cutover hybrid mix.
- java.text.DecimalFormat rounds the double's *exact* binary value with HALF_EVEN, not the
  shortest digits: 2.675 -> "2.67" at 2dp, 0.0005 -> "0.001" at 3dp, -0.05 -> "-0.1" at 1dp.
  The port's formatter therefore starts from Decimal(value). (String.format "%.1f" in
  getObservationValue is a different rounding — HALF_UP via javacompat — and is not shared.)
- ExportHelper.getObservationValue's FHIR Condition branch can never complete in Java: the
  value is cast to HealthRecord.Entry, and a org.hl7.fhir.dstu3.model.Condition is not an
  Entry, so it always throws ClassCastException (the probe records ERR:ClassCastException).
  The port marks the branch with a FhirCondition boundary class and raises TypeError there;
  no Python record can hold a FHIR object (FHIR export is out of scope).
- CSVFileManager quirk, reproduced: with neither included_files nor excluded_files set, the
  Java else-branch still runs propStringToList(""), and "".split(",") is [""], which
  normalizes to excluded_files == [".csv"] (harmless: no resource is named ".csv").
- CSVFileManager append mode never writes a header in single-file mode — not even for a
  file it just created (the header write is guarded by `if (!append)`). In multi-file mode
  the header is written when resourceCount % maxLinesPerFile == 1. Both reproduced.
- CSVFileManager.getWriterForMultipleFiles returns null in Java when the first count does
  not satisfy count % maxLinesPerFile == 1 (always, when maxLinesPerFile == 1); the write
  then NPEs. The port returns None from get_writer and raises TypeError at the write.
- Exporter.writeNewFile/overwriteFile use Files.write(path, singleton(contents)), which
  appends the platform line separator after the contents; the port writes contents + "\n".
- Exporter flag handling follows issue #25: the FHIR (stu3/dstu2/R4), hospital/practitioner
  (post-completion) and metadata exporters are ignored with a one-time-per-flag warning on
  stderr; every other non-CSV exporter flag set to true raises
  NotImplementedError("... out of scope"), as do the terminology service, queued FHIR
  export, ServiceLoader custom exporters, code mappers (BFD/RIF) and TransitionMetrics
  (no such module exists in the port yet).
- Person/Claim test doubles: the parity and unit tests script records on the
  tests.unit.test_health_record person_double plus tests/parity/export_doubles.ClaimDouble
  (T14 plumbing: the constructor's single randUUID draw and the items list; cost behaviour
  is not modelled). The cause-of-death filter scenario is gated on T22 (DeathModule.process
  is still a stub) in the parity suite, and the corresponding JUnit port is skipped with
  the same reason in tests/unit/test_exporter.py.
